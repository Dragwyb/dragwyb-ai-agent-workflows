# Feature Roadmap

Ordered, independently shippable increments. Each item follows the Section 9 development loop in full (Analyze → Design → Explain → Implement → Self-review → Security review → Performance review → WPCS/standards review → Refactor → Report) before the next item begins. Status and review notes are appended to each item as it completes.

1. **Core plugin bootstrap + activation/deactivation** — main file, container, autoloading, requirements check, activation/deactivation/uninstall skeleton (no tables yet beyond a version option).
2. **Database layer + Workflow CRUD** — migrations for `wfa_workflows`, `wfa_workflow_nodes`; `WorkflowRepository`; `WorkflowService`; internal-only (no UI/REST yet).
3. **REST API for workflows** — `WP_REST_Controller` for workflow CRUD with schema + permission callbacks.
4. **Admin shell + menu** — top-level admin menu, screen scaffolding, scoped asset enqueueing.
5. **Node/trigger/action registry** — `NodeTypeRegistry`, `TriggerInterface`, `ActionInterface`, first built-in node types (e.g. WP hook trigger, HTTP request action).
6. **Visual builder shell (front-end)** — React app shell, canvas rendering, node palette, save/autosave wired to the REST API.
7. **Execution engine (synchronous)** — `WorkflowExecutionService`, `NodeExecutionService`, `wfa_workflow_runs` / `wfa_workflow_run_logs` tables and repositories.
8. **Background/queued execution** — WP-Cron-driven batch claiming for webhook/async runs, retry/backoff.
9. **Logging & execution history UI** — paginated runs list, run detail view, re-run action.
10. **Settings screens** — general, retention/logging, advanced; uninstall opt-in data removal setting.
11. **Connections + credential encryption** — `wfa_connections` table, `ConnectionService`, encryption-at-rest via `wp_salt()`-derived key.
12. **First real integrations** — WordPress core hooks trigger, outbound HTTP action, email action.
13. **Webhooks (inbound)** — `wfa_webhooks` table, public ingress endpoint, optional signing secret + IP allow-list enforcement.
14. **Roles & capabilities** — custom capabilities layered over `manage_options`.
15. **Additional integrations** — expand catalog incrementally based on user demand (forms plugin, WooCommerce, etc.), one integration per increment.
16. **Onboarding & polish** — empty states, guided first workflow, accessibility pass on the builder.
17. **Extensibility documentation** — finalize `/docs/hooks-reference.md` against all hooks actually shipped.

This list will be updated as work progresses; completed items get a review summary appended below their entry.

### 3. REST API for workflows — done

**Built:** `src/Rest/WorkflowsController.php`, a `WP_REST_Controller` subclass exposing `wfa/v1/workflows` — collection `GET`/`POST`, item `GET`/`PUT`/`PATCH`/`DELETE`, and a custom `POST .../{id}/restore` action for un-trashing. Includes a full JSON-Schema `get_item_schema()`, `get_collection_params()`, and `prepare_item_for_response()` with `_links` (self/collection), following the same `WP_REST_Controller` contract WordPress core itself uses (`get_endpoint_args_for_item_schema()`, `get_public_item_schema()`, `X-WP-Total`/`X-WP-TotalPages` pagination headers, `{deleted, previous}` delete response) — a deliberate choice to use documented core conventions rather than the reference plugin's own bespoke router. `src/Rest/RestApi.php` is a thin `rest_api_init` bootstrap so `Plugin::load()` only gains one delegated call. Node-level (`workflow_nodes`) REST endpoints are intentionally out of scope for this increment.

**Self-review:** Confirmed every route has an explicit `permission_callback`. Confirmed `update_item()` runs `title`/`graph`/`settings` through `WorkflowService::update()`'s own validation before separately calling `changeStatus()` when a `status` field is present, so status changes can't bypass the enum check. Confirmed `delete_item()` and `restore_item()` both look the workflow up first and return a 404 before attempting the mutation, rather than inferring "not found" from the service's boolean return alone. Confirmed `graph`/`settings` are cast to `(object)` in `prepare_item_for_response()` so an empty PHP array never serializes as JSON `[]` when the schema promises an `object`.

**Security review:** Every `*_permissions_check` uses `current_user_can('manage_options')`, returning `rest_authorization_required_code()` (distinguishes 401 logged-out vs 403 logged-in-but-forbidden) — no route uses `__return_true`. No manual nonce check was added beyond that: WordPress's own `rest_cookie_check_errors` filter already enforces `X-WP-Nonce` on cookie-authenticated REST requests before any permission callback runs, so an additional check would be redundant and isn't the standard REST-API pattern. Write endpoints are validated in two independent layers — the JSON-Schema `args` (type/enum, `sanitize_text_field` on `title`) generated by `get_endpoint_args_for_item_schema()`, and `WorkflowService`'s own domain validation (non-empty title, status enum) — neither layer trusts the other. No request data reaches SQL or HTML directly; every response goes through `rest_ensure_response()`.

**Performance review:** The list endpoint delegates straight to the already-indexed, paginated `WorkflowRepository::paginate()` from item 2; `per_page` is clamped to `[1, 100]` at the schema level in addition to the repository's own clamp, so no unbounded query is reachable from this controller. `get_item`/`get_items` each issue exactly one `SELECT` — node data is deliberately not joined/expanded on the workflow response yet, avoiding an N+1 the reference product doesn't obviously guard against either.

**Standards review:** PHP 7.4 compatibility maintained — no union return types on permission-check/callback methods (matching how `WP_REST_Controller`'s own parent methods are also left untyped), documented instead via PHPDoc `@return`. WPCS-style array/spacing conventions verified manually (no `phpcs` CLI in this environment — same known gap as items 1–2).

**Refactor:** Caught during self-review: the schema-derived `POST` args would have advertised an accepted `status` field even though `create_item()` never forwards it (new workflows always start as `draft`, enforced in `WorkflowService::create()`). Added `getCreateArgs()` to strip `status` from the create-only arg set so the advertised API surface matches actual behavior.

**Deferred / follow-up:** Same PHPCS/PHPUnit/PHPStan CLI gap as items 1–2, still unresolved. This increment is verified structurally only — no running WordPress + MySQL environment is available in this session to exercise `wfa/v1/workflows` over real HTTP; flagged for a manual or CI smoke test before this item is considered fully verified against Section 12's gates. Node-level REST endpoints are deferred to whichever later increment first needs them (builder shell, item 6, or execution engine, item 7).

### 4. Admin shell + menu — done

**Built:** `src/Admin/AdminPage.php` (the contract every screen implements: `slug()`, `pageTitle()`, `menuTitle()`, `capability()`, `render()`, `enqueueAssets()`); `src/Admin/Menu.php` (registers the top-level `Workflow Automate` menu on `admin_menu` and enqueues a page's assets only when that exact screen is active, keyed off the real hook suffix returned by `add_menu_page()`/`add_submenu_page()` — never plugin-wide); `src/Admin/Pages/WorkflowsPage.php` (the first, and for now only, screen); `src/Admin/WorkflowsListTable.php` (extends core `WP_List_Table` — idiomatic wp-admin UI, not a bespoke table — with an All/Draft/Active/Paused/Trash view switcher, pagination, and row actions); `src/Admin/WorkflowActionsController.php` (the single `admin-post.php` handler backing trash/restore/delete). Extended `WorkflowRepository::paginate()` with an `only_trashed` flag so the Trash view's pagination total is accurate (a small, backward-compatible addition — existing callers are unaffected). Added `assets/admin/css/admin.css`, enqueued only on this one screen.

Per architecture §2.4 the eventual navigation is Dashboard/Workflows/Runs/Connections/Webhooks/Settings, but Runs, Connections, Webhooks, and Settings have no backing service yet (items 7, 10, 11, 13) — registering menu entries for them now would be dead navigation pointing at nothing, so only the Workflows screen was added. `Menu` takes an array of `AdminPage`s, so each later item adds its own page class without this class changing. Creating/editing a workflow's actual content is also deferred to the builder (item 6) — the only screen that will have anywhere meaningful to send a user after those actions; this increment covers viewing, filtering, trashing, restoring, and permanently deleting only.

**Self-review:** Confirmed the top-level menu and its first submenu entry share one slug (the standard WordPress technique for giving that row its own label instead of an auto-generated duplicate) so both routes resolve to the same, single screen. Confirmed `WorkflowActionsController::perform()` checks the workflow actually exists before calling `delete()`/`restore()` — without that check, a request for a nonexistent id would still show a "success" notice, because the underlying repository's `$wpdb->update()`-based methods treat "0 rows affected, no SQL error" as success. Confirmed `column_default()`'s `updated_at` case converts the GMT-stored timestamp to the site's local time via `get_date_from_gmt()` before formatting, rather than passing it straight to `mysql2date()` (which assumes local time) — an incorrect display offset would otherwise show on any site not running UTC.

**Security review:** `WorkflowsPage::render()` and `WorkflowActionsController::handle()` both independently check `current_user_can('manage_options')` (the page callback isn't solely relied upon — `admin-post.php` is reachable directly). Every row action (trash/restore/delete) is a `POST` form carrying a nonce scoped to that specific operation *and* id (`wfa_workflow_action_{op}_{id}`), verified with `check_admin_referer()` before anything runs — a stolen/replayed nonce for one workflow's "trash" action cannot be reused against a different id or operation. Deliberately rendered as `<form>`/`<button type="submit">` rather than `<a href>` row-action links: this is a stricter reading of Section 5's "do not perform state changes on GET requests" than WordPress core's own list tables apply (core uses nonce-protected GET links for the same pattern), chosen because the instructions call this out explicitly as its own CSRF-prevention rule. All read-only inputs (`$_GET['page']`, `$_GET['status']`, `$_GET['paged']`, `$_GET['wfa_notice']`) are sanitized (`sanitize_key()`/`absint()`) and only ever used for routing/filtering/array-key lookups against fixed allow-lists — never echoed back or interpolated into a query. All dynamic output goes through `esc_html()`/`esc_attr()`/`esc_url()` at the point of output.

**Performance review:** The list table's query is paginated (fixed page size of 20, matching the repository's existing default) and reuses the already-indexed `WorkflowRepository::paginate()` from item 2 — no unbounded queries. Assets are enqueued only on this one admin screen (verified via the real hook suffix, not a guess at the page slug), satisfying Section 6 directly. No new database queries were added beyond what `WorkflowService`/`WorkflowRepository` already provide.

**Standards review:** Followed the standard `WP_List_Table` extension pattern (`get_columns()`, `prepare_items()`, `column_default()`, `get_views()`) used throughout wp-admin itself. PHPDoc complete on all new classes/methods; `declare(strict_types=1)` used throughout. Fixed one i18n issue caught during this review: an early draft stored notice strings in a class constant and ran them through `esc_html__()` at render time — translation-extraction tooling can't see through a variable passed to `__()`, so the messages were moved into a small method that calls `__()` on each literal string directly, with `esc_html()` (not `esc_html__()`) used at the point of output. WPCS-style spacing/array syntax verified manually (no `phpcs` CLI in this environment — same known gap as items 1–3).

**Refactor:** Removed a hardcoded `'wfa-dashboard'` string literal duplicated between `WorkflowsPage::slug()` and `WorkflowActionsController`'s redirect target; the controller now takes the target slug as a constructor argument (set once, in `Plugin::registerAdmin()`, from the actual `WorkflowsPage` instance) instead of repeating the literal.

**Deferred / follow-up:** Same PHPCS/PHPUnit/PHPStan CLI gap as items 1–3. Verified structurally only — no running WordPress admin to click through in this session; flagged for a manual smoke test (page loads, each row action, each view filter, pagination) before this item is considered fully verified against Section 12's gates. The Trash view link is always shown even when there is nothing trashed (core's own list tables typically hide an empty Trash view) — a minor polish item, not a functional gap, left for a later pass. Bulk actions (e.g. bulk-trash) were intentionally left out of this first pass to keep the increment tight; single-row actions cover the same ground for now.

### 5. Node/trigger/action registry — done

**Built:** `src/Domain/Contracts/{NodeTypeInterface,TriggerInterface,ActionInterface}.php` (the public extension contracts — `NodeTypeInterface` is an internal-only shared-metadata base so `NodeTypeRegistry` doesn't duplicate handling for both kinds; third-party code only ever implements `TriggerInterface` or `ActionInterface`); `src/Service/NodeTypeRegistry.php` (a plain, framework-light collection keyed by slug, with a `_doing_it_wrong()` notice on slug collisions); `src/Integration/Triggers/WpHookTrigger.php` and `src/Integration/Actions/HttpRequestAction.php` (the two built-ins the roadmap names explicitly); `src/Integration/BuiltInNodeTypes.php` (registers those two on the new public `wfa/nodes/register` action). Wired into `Core\Plugin` via a new `registerNodeTypes()` step.

Resolved two naming inconsistencies between the original architecture draft and this implementation, documented in `docs/internal/architecture.md`: a single `NodeTypeRegistry` replaces the draft's separate `TriggerRegistry`/`ActionRegistry` (they'd have shared near-identical code), and the Integration layer bullet's stray `IntegrationInterface` name is corrected to `TriggerInterface` (matching §2.6's public interfaces list, which was already correct).

**Self-review:** Confirmed `TriggerInterface::bind()` and `ActionInterface::execute()` are shaped so the execution engine (item 7) can consume them without a redesign — `bind()` takes a generic `$on_fire` callback rather than anything execution-engine-specific, and `execute()` returns a plain result array rather than throwing for expected failures (an HTTP timeout is data, not an exceptional program state). Confirmed `NodeTypeRegistry` has zero WordPress hook knowledge of its own (trivially unit-testable); `Plugin` alone owns firing the extension point.

**Security review:** `HttpRequestAction::execute()` uses `wp_safe_remote_request()` — WordPress's own SSRF-guarding wrapper (applies `reject_unsafe_urls`, blocking requests to internal/private network addresses) — instead of the unguarded `wp_remote_request()`, directly implementing the architecture doc's "no open HTTP proxy endpoint" decision (opportunity #1) now that a real outbound-HTTP node type exists. The request URL is passed through `esc_url_raw()` before use; the HTTP method is validated against an allow-list (`GET`/`POST`/`PUT`/`PATCH`/`DELETE`), defaulting to `GET` for anything else, so a malformed/unexpected method value can't reach the HTTP client unchecked. `WpHookTrigger::bind()` does not evaluate or execute the configured hook name in any way beyond passing it to `add_action()` as a hook name string — there is no `call_user_func()`-on-arbitrary-string pattern here that could be abused.

**Performance review:** `NodeTypeRegistry` is an in-memory array lookup (no queries, no I/O). `wfa/nodes/register` fires exactly once per request, on `init` — not per-admin-page-load-with-extra-conditions like the migration re-check, and not repeated per node/workflow. `HttpRequestAction` sets an explicit 15-second timeout so a slow third-party endpoint can't hang a request indefinitely once the execution engine (item 7) starts calling it synchronously.

**Standards review:** PHPDoc complete on all new interfaces/classes; `declare(strict_types=1)` throughout. Caught and fixed during this review: `_doing_it_wrong()`'s arguments were initially wrapped in `esc_html()`, which isn't the correct pattern for that function (it's a developer-facing debug/logging call, not something being echoed into a page) — removed the unnecessary escaping.

**Refactor:** Caught during self-review: `wfa/nodes/register` was originally going to fire synchronously inside `Plugin::registerNodeTypes()` (itself called during our own `plugins_loaded` handler), which would make whether a third-party plugin's registration "wins the race" depend on plugin load order — a real, if subtle, extensibility bug. Fixed by deferring the actual `do_action()` call to `init`, by which point every plugin's `plugins_loaded` callback (the most common place a plugin would hook this from) has already run.

**Deferred / follow-up:** Same PHPCS/PHPUnit/PHPStan CLI gap as items 1–4. Nothing yet calls `NodeTypeRegistry::trigger()`/`action()`/`triggers()`/`actions()` or invokes `bind()`/`execute()` end-to-end — that lands with the execution engine (item 7) and the builder's node palette (item 6), both of which will read from this registry rather than hardcoding node type lists. `HttpRequestAction` does not yet use `$context` (prior node outputs/trigger payload) to template the URL/body — deliberately deferred, since templating syntax is a design decision better made once the execution engine defines what `$context` actually contains.

### 6. Visual builder shell (front-end) — done

**Built:** A React app (`assets/builder/src/`, built with `@wordpress/scripts` into `assets/builder/build/`) mounted on a new, menu-hidden `wfa-builder` admin page (`src/Admin/Pages/BuilderPage.php`), reached via "Add New"/"Edit" links added to the Workflows list (`WorkflowsPage`/`WorkflowsListTable`). The app has a header (editable title, manual Save button, autosave status indicator, back-to-list link), a left node palette grouped into Triggers/Actions, a canvas that renders each graph node as a draggable/keyboard-nudgeable card, and a right-hand config panel whose fields are generated generically from each node type's `configSchema()` — not hand-coded per node type, so a third-party node type registered via `wfa/nodes/register` (item 5) needs zero front-end changes to appear and be configurable. Autosave is debounced (1.5s after the last edit) with a manual Save button always available, per architecture §2.4.

Two small, necessary additions this item's scope required but wasn't itself named for: a read-only `GET /wfa/v1/node-types` REST endpoint (`src/Rest/NodeTypesController.php`) exposing the item-5 `NodeTypeRegistry` to JavaScript — the palette has no other way to know what node types exist — documented in `docs/rest-api.md`; and an `AdminPage::showInMenu()` addition to the item-4 admin contract, so `BuilderPage` can be a fully routed, capability-checked admin screen (`admin.php?page=wfa-builder`) without adding a second, redundant row to the visible menu (implemented via `add_submenu_page()` immediately followed by `remove_submenu_page()` — the standard WordPress technique for this).

**Self-review:** Verified the "create new workflow" flow doesn't double-create on refresh — the app calls `POST /wfa/v1/workflows` only when it mounts with no `workflow` query arg, then immediately swaps the URL to include the new id via `history.replaceState()` (not `pushState`, so the browser's Back button doesn't return to a stale "new workflow" URL either). Verified the autosave effect skips its first run after data loads (a `skipNextAutosaveRef` flag) so simply opening an existing workflow doesn't immediately mark it "unsaved" and fire a needless `PUT`. Verified drag vs. click is disambiguated by a small movement threshold (3px) so clicking a node to select it doesn't require a perfectly still pointer. Verified the JSON config field (for `object`/`array`-typed config, e.g. HTTP headers) keeps invalid JSON local to the textarea with an inline error rather than committing a parse failure into the graph.

**Security review:** `BuilderPage::render()`/`enqueueAssets()` gate on `current_user_can('manage_options')`, matching every other admin/REST surface in this plugin; the new `NodeTypesController::permissionsCheck()` does the same, returning `rest_authorization_required_code()` like `WorkflowsController` does. All REST calls from the app go through `@wordpress/api-fetch`, which WordPress core auto-configures with the `X-WP-Nonce`/REST-root middleware the moment the `wp-api-fetch` script is enqueued — no bespoke nonce plumbing was written or could drift out of sync with core's own. The only server-side request input this item reads is `$_GET['workflow']`, sanitized with `absint()` and used only to select which workflow to fetch over the (independently-authorized) REST API — never interpolated into SQL or echoed. All dynamic content in the React tree is rendered via JSX (auto-escaped); no `dangerouslySetInnerHTML` is used anywhere in the app. The bootstrap data passed to the page via `wp_add_inline_script` is `wp_json_encode()`d and contains only an integer and a `admin_url()`-generated string — no user-controlled data crosses that boundary.

**Performance review:** The compiled bundle is small (~12 KB JS, ~3.5 KB CSS, unminified-source before gzip) because `@wordpress/element`/`@wordpress/components`/`@wordpress/api-fetch`/`@wordpress/i18n` are externalized to WordPress's own bundled copies rather than being bundled again — verified by inspecting `assets/builder/build/index.asset.php`'s generated dependency list. Assets are enqueued only on the `wfa-builder` screen (same hook-suffix-gated mechanism as item 4's `Menu`), never plugin-wide. Autosave is debounced to one `PUT` per 1.5 seconds of inactivity rather than one per keystroke; the node-types catalog and the workflow are fetched exactly once per page load. `GET /wfa/v1/node-types` does no database I/O — it's a single in-memory registry read.

**Standards review:** `npm run build` (via `@wordpress/scripts`) and `npm run lint:js` were both actually run and pass clean in this session (node/npm are available in this environment, unlike PHP/Composer — see items 1–5's recurring gap) — this is the first roadmap item verified by a real, automated tool run rather than manual read-through alone. All new PHP carries `declare(strict_types=1)`, ABSPATH guards, and full PHPDoc, consistent with items 1–5; WPCS conformance for the PHP side is still manual-only (same known CLI gap).

**Refactor:** Caught while building: `@wordpress/scripts` v28+ switched to the automatic JSX runtime, which depends on the `react-jsx-runtime` script handle that WordPress core only registers from 6.6 onward — silently incompatible with this plugin's declared `Requires at least: 5.8`. Pinned `@wordpress/scripts` (and the runtime `@wordpress/*` packages) to the last `^27.x`/pre-6.6-transform generation instead, documented in `webpack.config.js`. Also caught: `wp-scripts build`'s `MiniCssExtractPlugin` config names its output `style-index.css` (plus an auto-generated `style-index-rtl.css`), not `index.css` as initially assumed — fixed the enqueue path and added `wp_style_add_data( 'wfa-builder', 'rtl', 'replace' )` so WordPress automatically swaps in the RTL stylesheet for RTL locales, which the initial version omitted entirely. Fixed `.eslintrc`'s `"build/**"` ignore pattern, which (like gitignore patterns generally) only anchors to the repo root and so didn't actually exclude the nested `assets/builder/build/` output — `eslint .` was linting the compiled, minified bundle until this was corrected.

**Deferred / follow-up:** Same PHPCS/PHPUnit/PHPStan CLI gap as items 1–5, plus: no running WordPress admin available in this session to click through the actual builder UI end-to-end (verified via a real `npm run build`/`lint` pass and structural/code review only) — flagged for a manual smoke test (open the page, add/move/select/delete nodes by mouse and by keyboard, edit config fields, confirm autosave and manual save both persist, reload and confirm state survives) before this item is considered fully verified against Section 12's gates. Drag-to-connect wiring between nodes and undo/redo are explicitly out of scope for this increment (per architecture §2.4's own phasing) — `graph.connections` is persisted but always empty for now. Whether a workflow should be limited to a single trigger node is an open product question left for the execution engine (item 7) to answer, since that's what gives the constraint actual meaning; the palette does not currently prevent adding more than one.

### 7. Execution engine (synchronous) — done

**Built:** `src/Database/Migrations/{CreateWorkflowRunsTable,CreateWorkflowRunLogsTable}.php` (`wfa_workflow_runs`, `wfa_workflow_run_logs`, exactly as designed in architecture §2.3, registered into `SchemaMigrations`); `src/Domain/{WorkflowRun,WorkflowRunLog}.php` (immutable entities, same `fromRow()` pattern as items 1–2); `src/Persistence/{WorkflowRunRepository,WorkflowRunLogRepository}.php` (insert/finish/find plus a paginated `paginateForWorkflow()` for the future run-history UI); `src/Service/NodeExecutionService.php` (runs one node via `NodeTypeRegistry::action()`, catching `Throwable` so a misbehaving third-party action can't take down a whole run); `src/Service/WorkflowExecutionService.php` (runs a workflow start-to-finish: creates a `wfa_workflow_runs` row, loops non-trigger nodes in graph order, writes one `wfa_workflow_run_logs` row per node, rolls the per-node outcomes up into a `success`/`failed`/`partial` run status, increments `run_count`). Also shipped the four execution-lifecycle hooks architecture §2.6 had already named as planned — `wfa/workflow/before_run`, `wfa/workflow/after_run`, `wfa/node/before_execute`, `wfa/node/after_execute` — documented in `docs/hooks-reference.md`.

Two things this item's scope required but wasn't itself named for, both flagged during design rather than discovered mid-implementation:

- **`WorkflowService::syncNodesFromGraph()`** — the builder (item 6) only ever writes a workflow's whole graph as JSON onto `graph_json`; nothing has ever kept the item-2 `wfa_workflow_nodes` table in sync with it, because nothing read that table until now. `wfa_workflow_run_logs.node_id` needs a real, stable row id to reference, so this method reconciles `wfa_workflow_nodes` from `graph_json` (insert/update/delete by `client_node_id`) immediately before a run, not on every autosave — the table is now load-bearing for the first time.
- **`src/Integration/WorkflowTriggerBinder.php`** — item 5 built `TriggerInterface::bind()` but explicitly deferred actually calling it to "the execution engine" (see item 5's own Deferred note). This class closes that loop: on `init` (priority 20, after node type registration), it binds every active workflow's trigger node(s) — reading trigger config straight from `graph_json` rather than the lazily-synced `wfa_workflow_nodes`, since binding must happen this early in the request and only `graph_json` is guaranteed fresh at that point — to `WorkflowExecutionService::run()`. This is also what answers item 6's open question: **a workflow may have more than one trigger node**; each is bound independently, and any one of them firing runs the same fixed action sequence. Nothing prevents multiple triggers, and nothing needs to — without a connections graph, actions aren't tied to any specific trigger anyway.

A minimal `POST /wfa/v1/workflows/{id}/run` REST action (`WorkflowsController::run_item()`) was also added, returning the completed run plus its per-node logs inline. A full paginated `wfa/v1/runs` resource is explicitly deferred to item 9 (Logging & execution history UI); this action exists purely so the engine is testable/usable now, documented in `docs/rest-api.md`.

**Self-review:** Confirmed trigger nodes never enter `NodeExecutionService::execute()` — `WorkflowExecutionService::run()` filters them out via `NodeTypeRegistry::trigger()` before the loop body, so a workflow's own trigger node never logs a spurious "no action registered" failure against itself. Confirmed the "fail fast" loop's invariant holds structurally (`executed` and `succeeded` can only ever differ by at most 1, since the loop breaks on the first failure) and that `finalStatus()`'s three branches (`success`/`failed`/`partial`) cover every reachable combination, including the vacuous zero-executable-nodes case (treated as `success`). Confirmed `WorkflowService::delete($id, true)` now cascades through logs → runs → nodes → the workflow itself, resolving run ids before deleting logs (which are keyed by `run_id`, not `workflow_id`) rather than assuming a shortcut cascade path exists.

**Security review:** The new `POST .../run` route reuses `update_item_permissions_check()` (`manage_options`, `rest_authorization_required_code()`), consistent with every other write route on `WorkflowsController` — no new permission model introduced. `NodeExecutionService::execute()` never calls user/request input directly; it only ever calls the already-vetted `ActionInterface::execute()` contract (see item 5's `HttpRequestAction` security review — `wp_safe_remote_request()`, allow-listed HTTP methods — unchanged here). Catching `Throwable` around that call is a deliberate hardening measure, not a way to hide errors: a third-party action that throws (violating its own "report, don't throw" contract) is converted into a normal failed-node log entry with the exception's message, rather than a fatal error that would take down the whole request (and, on the live-trigger path, whatever unrelated WordPress request happened to fire the hook). `WorkflowTriggerBinder` never evaluates or calls anything from graph JSON beyond passing already-validated `type`/`config` values into the same `TriggerInterface::bind()` contract item 5 already reviewed — no new `call_user_func()`-on-arbitrary-string surface.

**Performance review:** `WorkflowTriggerBinder::bindActiveWorkflows()` runs on `init` on every request (front-end, admin, REST, cron, AJAX) — an inherent, deliberate cost of the "trigger via live WP hooks" model chosen in item 5, not an oversight here; mitigated with a single indexed (`status`) query capped at `MAX_ACTIVE_WORKFLOWS = 100` (matching `WorkflowRepository::paginate()`'s own `per_page` ceiling, so the constant reflects a real limit rather than an aspirational one that would be silently clamped down anyway), and it's a no-op beyond that one query when there are zero active workflows. `syncNodesFromGraph()` is called lazily (once per run, not once per autosave) specifically to avoid paying a reconciliation cost on every keystroke-triggered save from the builder. `NodeExecutionService`/`WorkflowExecutionService` add no new N+1 patterns: one `wfa_workflow_runs` insert, one `wfa_workflow_run_logs` insert per executed node, one `run_count` update per run — `WorkflowRepository::incrementRunCount()` uses an atomic `run_count = run_count + 1` SQL expression instead of a read-then-write round trip, so concurrent runs of the same workflow can't lose an increment to a race condition.

**Standards review:** `declare(strict_types=1)`, ABSPATH guards, and full PHPDoc across all new files, consistent with items 1–6. `Throwable` (not just `Exception`) is caught deliberately in `NodeExecutionService` — PHP 7.4 (this plugin's floor) supports it natively, and it also catches `Error` subclasses (e.g. a `TypeError` from a badly-written third-party action), which is exactly the class of failure this catch exists to contain. WPCS conformance is manual-only, same known CLI gap as items 1–6.

**Refactor:** Caught during design, before any code was written: an initial sketch had `syncNodesFromGraph()` running inside `WorkflowService::update()` (i.e. on every graph save), which would call it on every autosave tick for no benefit, since nothing reads `wfa_workflow_nodes` until a run happens — moved the call into `WorkflowExecutionService::run()` instead. Also caught: `WorkflowTriggerBinder`'s callback initially only declared one parameter (`$payload`), relying on PHP silently ignoring the second argument `TriggerInterface::bind()`'s documented `$on_fire` signature actually passes (`$payload, $config`) — corrected to declare both explicitly, matching the interface's own PHPDoc contract rather than depending on an implicit PHP behavior. Also caught: `WorkflowTriggerBinder::MAX_ACTIVE_WORKFLOWS` was initially set to 200, but `WorkflowRepository::paginate()` (called underneath) clamps `per_page` to a ceiling of 100 regardless — the constant would have silently promised a limit the repository never actually honored. Lowered to 100 to match the real, enforced ceiling.

**Deferred / follow-up:** Same PHPCS/PHPUnit/PHPStan CLI gap as items 1–6, plus no running WordPress + MySQL environment in this session to actually fire a WP hook end-to-end and watch a live-triggered run happen — verified structurally/by code review only; flagged for a manual smoke test (activate a workflow with a `wp_hook_trigger` bound to e.g. `wp_login`, an `http_request_action` pointed at a request-bin URL, log in, confirm a `wfa_workflow_runs`/`wfa_workflow_run_logs` row appears; also exercise `POST /wfa/v1/workflows/{id}/run` directly) before this item is considered fully verified against Section 12's gates. Node execution order is graph order and failure handling is fail-fast, both explicitly flagged in-code and in the architecture doc as placeholders for real DAG-based ordering (needs item 6's deferred connections) and a configurable per-workflow on-failure setting (item 10). `$context` passed to `ActionInterface::execute()` accumulates prior node outputs but nothing yet lets a node's config *reference* that data (templating syntax, e.g. `{{node.x.output}}`) — still deferred, per item 5's own note, until real usage patterns from later integrations (item 12+) inform the syntax. Background/queued execution (retries, webhook batching) is explicitly item 8, not this one; every run here is synchronous and blocks its calling request for its full duration.
